# 空 EOF 恢复重试设计

## 现场证据

测试站的失败都表现为：Kiro 返回 HTTP 200 和 `contextUsage`，但没有正文、thinking 或完整工具调用，随后 EOF。RS 尚未交付语义事件时会重试一次，但 v0.9.20 第二次仍发送完全相同的请求体，所以稳定得到 `upstream_empty_response`。

2026-07-25 的两个快照说明故障不是单一的“历史图片过多”：

- `snap_cda78...`：7 条消息、2 张当前轮图片、约 6.3% 上下文占用，连续空 EOF。当前实现不会压缩当前轮图片，也没有可用的恢复请求体。
- `snap_aa71...`：两个并行 PowerShell `tool_use` 与两个 `tool_result` 的 ID、顺序和配对全部合法，但工具结果续轮连续空 EOF。
- 对 `snap_aa71...` 的真实请求做在线单变量回放：原请求稳定 HTTP 502；替换第二个 1326 字符的工具输出后，同一历史、73 个工具定义和模型立即 HTTP 200；保留 512 字符前缀可恢复，保留 1024 字符仍失败。移除 thinking、metadata、output_config 或 system 均无效。

因此恢复请求体必须同时处理两类上游异常：图片载荷，以及会令 Kiro 静默 EOF 的工具结果内容。正常首轮请求不得修改。

## 目标

1. 首次请求完整保留客户文本、工具结果和当前轮图片。
2. 只有首轮完全空 EOF、且未向客户端交付正文或工具时，才发送唯一一次恢复请求。
3. 恢复请求降低全部图片清晰度；历史图片仍超预算时，从最早图片开始淘汰，但至少保留最近 3 张历史图片，当前轮图片永不删除。
4. 恢复请求把当前轮每个工具结果限制为 512 个 Unicode 字符，并追加固定省略标记；未超过限制的结果不变。
5. 第二次仍为空时返回真实 HTTP 502 `upstream_empty_response`，让 NewAPI 切换兜底渠道。
6. 不影响 1 秒 SSE Ping、首字门控、缓存计量、usage、工具 ID 和正常请求延迟。

## 请求体分层

`PreparedKiroBodies` 只预生成正常首轮和明确长度超限所需的请求体。空 EOF 恢复体不在首轮前生成，避免当前图片解码、重编码增加正常请求首字延迟；handler 只有在首轮被分类为 `EmptyResponse` 后，才从实际发送的 `primary_body` 惰性生成恢复体。

| 请求体 | 使用时机 | 行为 |
| --- | --- | --- |
| `primary_body` | 正常首轮 | 现有常规历史图片预算，客户内容完整 |
| `threshold_retry_body` | 上游明确返回 `CONTENT_LENGTH_EXCEEDS_THRESHOLD` | 现有历史图片二级压缩，不截断工具结果 |
| 惰性空 EOF 恢复体 | 首轮完全空 EOF | 从首轮请求体生成；恢复级图片压缩、最旧历史图片淘汰、当前工具结果 512 字符上限 |

`prepare_retry_request_body` 仅在 `AttemptFailure::EmptyResponse` 时调用恢复生成器；没有安全变化或生成失败时仍只重试一次原请求。Schema 修复继续基于首轮请求体生成，其他失败保持原行为。严格 JSON 路径会把首轮失败分类传给第二次尝试，只在首轮为空 EOF 时叠加图片恢复，普通 JSON 格式修复不会降质图片。

## 图片恢复规则

- 正常首轮只压缩历史图片，沿用现有策略。
- 空 EOF 恢复体使用 `retryHistoryMaxDimension` 和 `retryHistoryJpegQuality` 重新编码历史图片与当前轮图片。
- 当前轮图片全部保留，即使恢复体仍超过软预算。
- 历史图片按消息顺序从最早开始淘汰，直到满足软预算或仅剩最近 3 张。
- 某条历史 user 消息因图片淘汰而没有任何内容时，写入固定中性占位文本 `[Historical image omitted during recovery]`，不改变消息顺序和工具配对。

## 工具结果恢复规则

- 只处理 `conversationState.currentMessage.userInputMessage.userInputMessageContext.toolResults`。
- 每个结果的文本按 Unicode 字符边界保留前 512 字符，追加 `\n[Tool result truncated during empty-response recovery]`。
- 不修改 `toolUseId`、`status`、`isError`、结果数量或顺序。
- 历史工具结果不修改，避免破坏已经完成的多轮工具语义。
- 该截断只存在于空 EOF 的第二次请求；首轮和明确长度阈值重试仍发送完整工具结果。

## 安全边界

透明重试必须同时满足：

- 当前是第一次上游尝试；
- 失败分类为 `EmptyResponse`：在流式 attempt 中包括正常 EOF 前零语义输出，以及零语义输出后的流读取错误或空闲超时。普通非流式 body 读取错误仍按传输故障使用原请求重试，避免纯网络抖动导致内容无故降质；
- 尚未提交正文、thinking 或工具调用；
- 尚未转发任何工具；
- 有安全恢复变化时使用恢复体，没有变化时沿用首轮请求体；
- 总共只允许一次透明重试。

收到 `contextUsage`、心跳或其他非语义帧不算成功。已交付任何语义内容后不得透明重试，避免重复工具和双重回复。

## 禁用并行工具调用

现场错误 `client disabled parallel tool use but upstream produced multiple tool calls` 的根因是：客户端设置了 `disable_parallel_tool_use=true`，但 Kiro 没有对应的原生请求字段，仍可能生成多个工具。旧实现先把全部工具块交付给流式客户端，最后才做数量校验并把整轮改成 `upstream_tool_choice_error`，因此客户会看到工具调用后突然中断；非流式则直接丢弃整轮并返回 502。

修复采用双层约束：

- 请求侧给所有可用工具追加固定提示，明确本轮最多调用一个工具；不复制客户 Schema 字段或值，不引入动态提示注入。
- 响应侧以首个观察到的工具 ID 为准。流式在原始 `tool_use` 分片进入 JSON 累积器之前占用本轮唯一工具槽，同一 ID 的后续分片继续拼接，其他 ID 的全部分片直接抑制；非流式使用相同规则。这样第二个工具即使 JSON 非法、半截 EOF 或与首个工具交错，也不会拖垮已选中的首个工具。
- 首个工具一旦完成 JSON 解析、进入 Schema 校验或发生 JSON 解析失败，唯一槽立即关闭；之后即使上游重放相同 ID，也不会产生第二次工具交付或覆盖首次失败。
- 非流式正文中的 `<invoke>` 只属于兼容捞回。存在已完成的原生结构化工具时，串行筛选优先保留该原生 ID，防止后出现的文本泄漏因归一化顺序反而覆盖真实工具。
- 第一个工具仍执行完整的名称映射、JSON 解析和 Schema 校验。即使第一个工具 Schema 无效，第二个工具也不会被交付；客户端收到第一个工具对应的稳定 Schema 错误，透明重试则使用全新的流上下文。RS 不伪造参数、不自动执行工具，也不把第二个工具挪到下一轮。
- `auto`、`any` 和指定工具三种策略都遵守相同边界。未设置 `disable_parallel_tool_use` 的请求保持原行为。

客户影响：显式禁用并行工具的客户端不再因 Kiro 额外生成工具而整轮中断，只会处理首个观察到的工具 ID。若该工具本身非法，仍返回它对应的稳定协议错误，不会改用第二个工具掩盖错误。需要多个工具时会由客户端通过后续轮次串行完成，可能增加轮次数，但符合客户端声明的能力边界。

## 客户影响

正常请求无行为变化。只有首轮已经完全失败时，第二次才可能收到低清图片或截断后的当前工具输出。与直接卡死或返回 502 相比，这会提高恢复概率；若恢复仍失败，客户收到真实 502，NewAPI 可以调度其他上游。工具 ID、工具执行次数和客户原始请求均不改变。

## 测试要求

至少覆盖：

1. `EmptyResponse` 使用恢复体，其他失败不误用。
2. 当前轮图片在恢复体中被压缩但不删除。
3. 历史图片从最早开始淘汰并保留最近 3 张。
4. 图片淘汰后的空历史消息使用固定占位文本。
5. 当前工具结果超过 512 字符时按字符边界截断、追加标记，ID/状态/数量不变。
6. `threshold_retry_body` 不截断工具结果。
7. 两次空响应返回真实 HTTP 502，且不发送成功终止事件。
8. 已交付正文或工具后不重试。
9. 流式与非流式路径行为一致。
10. 1 秒 Ping、SSE 门控、缓存计量、usage、Schema 修复与自动续写测试不回归。
